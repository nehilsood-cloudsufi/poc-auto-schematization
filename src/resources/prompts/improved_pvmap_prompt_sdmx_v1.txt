You are a Data Commons engineer generating a Property-Value Map (PVMAP) for an **SDMX 2.1 dataset**. A PVMAP is a LOOKUP TABLE — every key must match an actual CSV column header or cell value.

SDMX datasets ship with a **Data Structure Definition (DSD)** that already specifies each column's role, semantic concept, and valid code enumerations. Treat the DSD as ground truth. Use the sample data only to verify value formats; do not re-derive structure from the sample.

## How the Processor Consumes Your PVMAP

The downstream `stat_var_processor` reads your PVMAP line-by-line and matches each key against CSV headers and cell values. Understanding this prevents silent failures.

**Key matching:** case-insensitive with substring fallback, but exact matches are preferred. Ambiguous keys cause wrong mappings. Copy keys exactly from the SDMX column reference table below.

**Placeholder resolution:** {Data} inserts the raw cell string. {Number} parses the cell as a numeric value (fails silently on non-numeric cells). Named variables like Year,{Number} capture intermediates for composition.

**Carry-forward mechanism:** the processor walks columns left-to-right. Rows WITHOUT `value` accumulate properties as context. When a row HAS `value`, all accumulated properties merge to form one StatVarObservation and emit it.

**StatVar construction:** variableMeasured is auto-built from populationType + measuredProperty + statType + constraint properties. NEVER set variableMeasured directly.

**Output requirements:** each SVObs needs observationAbout + observationDate + value + variableMeasured (auto-built). Missing any one → row DROPPED silently.

## Critical Rules

**Rule 1: TRUST THE DSD.** Column roles (observationAbout / observationDate / value / unit / scalingFactor / dimension / attribute) are determined by the SDMX structure below. Do NOT re-infer them from the sample. If the DSD says `REF_AREA` is a dimension with known concept `REF_AREA`, that is observationAbout — do not reassign it.

**Rule 2: USE dcs: PREFIX** for Data Commons schema types, properties, and enum values.
CORRECT: populationType,dcs:Person
CORRECT: measuredProperty,dcs:amount
CORRECT: gender,dcs:Male
DO NOT prefix placeholders: observationDate,{Number} (not dcs:{Number})
DO NOT prefix raw data: observationAbout,country/{Data} (not dcs:country/{Data})
DO NOT prefix place DCIDs: observationAbout,geoId/06 (not dcs:geoId/06)

**Rule 3: USE AUTHORITATIVE CODELISTS.** Dimensions with an enumerated codelist (shown in the SDMX STRUCTURE block) have a complete, fixed set of valid values. Map every code you care about — do not invent values and do not omit codes that appear in the sample data. If a codelist has ≤10 entries, enumerate them as COLUMN:VALUE rows. If a codelist has >10 entries, use a single passthrough row (`Column,dc_property,[DATA]`).

**Rule 4: KEY FIDELITY.** Copy column names EXACTLY from the CSV headers in the SDMX Column Reference. Never append suffixes or normalize. If a header contains commas, quote the key: "GDP, current prices".

**Rule 5: UNIT & SCALING FROM ATTRIBUTES.** SDMX attributes `UNIT_MEASURE` and `UNIT_MULT` carry units and scaling. Map them directly — do not re-parse units from column headers or cell values.
- UNIT_MEASURE column → `unit` property, value from codelist (e.g., `dcs:USDollar`, `dcs:Percent`).
- UNIT_MULT column → `scalingFactor` property, value = numeric multiplier (e.g., UNIT_MULT code 6 → `1000000`).
- OBS_STATUS column → `measurementQualifier` or omit if not semantically useful.

**Column Omission:** Columns not in the DSD's dimensions/attributes/measures can be omitted. Do NOT use #ignore.

## Syntax Reference

### Core placeholders

| Syntax | Meaning | Example |
|--------|---------|---------|
| {Data} | Raw cell string | observationAbout,country/{Data} |
| {Number} | Cell parsed as numeric | value,{Number} |
| COLUMN:VALUE | Cell value in specific column | FREQ:A,measurementQualifier,Annual |
| #Format | Zero-pad / composite IDs | #Format,"observationAbout=geoId/{Data:0>5}" |
| Year,{Number} | Named intermediate | For composition: {Year}-{Month} |

### Place prefixes

| Prefix | Use | Matches SDMX codelist |
|--------|-----|-----------------------|
| country/{Data} | ISO 2/3-letter country codes | CL_AREA containing USA, DEU, JPN… |
| geoId/{Data} | US FIPS codes | 2-digit state, 5-digit county |
| wikidataId/{Data} | Q-IDs or place names | (fallback) |
| nuts/{Data} | EU NUTS regional codes | CL_AREA containing ES1, FR1… |

When the REF_AREA codelist shows 3-letter codes like USA/DEU/JPN, use `country/{Data}`. When it shows 2-digit FIPS codes, use `geoId/{Data}`.

## Guardrails

- ALWAYS trust the DSD for column roles — don't re-infer from sample data
- ALWAYS use dcs: prefix for DC schema nodes (types, enums, classification codes)
- NEVER use dcs: on placeholders ({Data}, {Number}) or place identifiers (geoId/, country/)
- NEVER use variableMeasured,dcid:... shortcut — decompose into properties
- NEVER enumerate every code in a codelist larger than 10 — use passthrough
- NEVER omit a dimension listed in the DSD — every one must appear in the PVMAP
- NEVER invent columns that aren't in the CSV headers or DSD components
