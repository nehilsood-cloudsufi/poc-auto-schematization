## 1. Identify Root Cause

### If Validation Failed (error analysis)

Look for these common error patterns:

#### Key Mismatch Errors
- "Key not found" → Key in PVMAP doesn't match column header exactly
- Check case sensitivity: "Year" vs "year" vs "YEAR"
- Check for whitespace: "Year " vs "Year"
- Check for special characters being escaped incorrectly

#### Missing Required Properties
- "observationAbout not found" → No place column mapped
- "value not mapped" → Numeric column not mapped with [NUMBER]
- "observationDate not found" → Date/year column not mapped

#### DCID Prefix Errors
- Values must be BARE identifiers (no "dcid:" or "dcs:" prefix)
- The processor adds prefixes automatically
- WRONG: "populationType,dcid:Person" → CORRECT: "populationType,Person"
- If dcid: prefixes appear in the PVMAP, instruct their removal

#### Column Mapping Errors
- Wrong column mapped to observationAbout (needs place/geo column)
- Wrong column mapped to observationDate (needs date/year column)
- Dimension column treated as value or vice versa

#### #Eval Expression Errors
- f-strings (f"...") NOT supported — processor uses eval()
- Nested double quotes break CSV parsing — use single quotes
- Suggest splitting complex logic into per-row #Eval with named variables

### If Validation Passed but Quality Low (quality analysis)

Look at the heuristic score breakdown to identify weak areas:
- Low row coverage: Are there missing dimension mappings?
- Low property coverage: Are observationAbout/observationDate/value mapped?
- Low column coverage: Which data columns weren't mapped?
- Low format score: Are [DATA]/[NUMBER] placeholders used correctly?

If Ground Truth Accuracy scores are available, use them as a signal:
- Low node accuracy means many PVMAP rows don't match expected patterns
- Low PV accuracy means property-value pairs within rows are incorrect
- If PV ACCURACY LOW: cross-reference StatVar analysis with schema vocab for fixes
- If QUALITY LOW: focus on structural improvements (coverage, format)

### If PV Accuracy Low (feedback_mode mentions "PV ACCURACY LOW")

The PVMAP structure is OK but property-value pairs don't match expected patterns.
Use the Schema Domain Context and StatVar Analysis above to identify specific issues:

#### Cross-Reference with Schema Vocab
- Compare generated properties against the property_vocabulary in the schema vocab
- Check if dimension values use proper DCIDs from the vocabulary, or if raw data strings are
  being passed through when enum DCIDs are expected
- Verify populationType matches one of the stat_var_skeletons for this domain

#### Analyze Generated StatVars
- Check the StatVar Analysis for corrupted or malformed values (broken CSV parsing, misplaced commas)
- Flag properties where raw data strings appear instead of dcid: references
- Identify dimension properties with suspiciously few unique values

#### Provide Enum Mapping Fixes
If the StatVar analysis shows raw strings on dimension properties that should use DCIDs:
- Suggest explicit Column:Value mappings instead of [DATA] passthrough
- Reference the schema_vocab property_vocabulary for valid DCID values in this domain
- Do NOT hardcode specific values — use the vocabulary as the source of truth

### Key Match Report Analysis
If the Key Match Report is provided above, use it to identify key issues:
- **UNMATCHED keys**: These PVMAP keys don't match any column header. Use the suggested correct header.
- **Unmapped columns**: These data columns aren't referenced in the PVMAP. Determine if they should be mapped:
  - Place/geo columns → MUST be mapped to observationAbout
  - Time/date columns → MUST be mapped to observationDate
  - Value/numeric columns → Should be mapped with value,[NUMBER]
  - Dimension columns → Should use COLUMN:VALUE enumeration
  - Metadata columns (source, notes) → Can be safely ignored

### Column Completeness Report
{column_completeness_report}

If must-map columns are listed as MISSING above:
- Place/time/value columns: This is CRITICAL — the PVMAP is broken without these. Add them immediately.
- Dimension columns: These cause StatVar collapse — rows with different dimension values will be treated as the same observation. Add COLUMN:VALUE rows for each unique value.
Refer to the PVMAP Skeleton in the original prompt for the suggested mapping pattern.

## 2. Interpret Processing Metrics

If processing metrics are provided above, use them to pinpoint issues:

### Coverage Quick-Reference

| Coverage | Diagnosis | Action |
|----------|-----------|--------|
| 0% (0 rows) | PVMAP keys don't match any data | Check exact column headers |
| < 50% | Major mapping gaps | Identify unmapped columns from patterns below |
| 50-90% | Partial — some value types failing | Fix specific failing patterns |
| 100% | All rows mapped | Focus on property/format/quality |

### Unmapped Value Patterns → Fixes

| Pattern | Example Values | Fix |
|---------|---------------|-----|
| state_code | AL, CA, TX | Map state column to observationAbout with FIPS codes |
| place_name | ALBERTVILLE CITY | Use FIPS column instead of name column |
| year | 2010, 2020 | Add observationDate mapping for year column |
| fips_code | 01, 06 | Use geoId/[DATA] with zero-padding |
| numeric_id | 10000500879 | Check if ID column should be mapped or excluded |
| enum | Male, Female | Add COLUMN:VALUE rows for each categorical value |
| numeric | 0.976, 12345 | Check if value column needs [NUMBER] mapping |

### Error Type Priorities
1. **pvmap dropped undefined property** — keys don't match data columns (most common)
2. **unresolved place** — observationAbout values can't resolve to DC places
3. **missing property** — required properties not mapped
4. **duplicate statvars** — multiple rows generating identical StatVars

### Output Property Cardinality Signals

| Property | Value = 1 | Meaning | Fix |
|----------|-----------|---------|-----|
| observationAbout | CRITICAL | All observations → same place | Wrong geo column; check unmatched for FIPS/state codes |
| observationDate | Check | All same date (may be OK for single-year) | Check unmatched for year patterns |
| value | CRITICAL | All same number | Value column not using [NUMBER] |
| variableMeasured | Very few | Dimensions collapsing | Unmapped dimension columns |

### Fragmentation Ratio (unique_statvars / total_observations)
- < 0.05: Compact (good for dimension-rich). 0.05-0.3: Healthy. 0.3-0.8: Moderate (check categorical columns). > 0.8: Nearly 1:1 — a dimension is treated as defining property; move to observationAbout/observationDate.

### StatVar Breakdown
- WITH observations: Working correctly. Low counts → some rows failing silently.
- Dropped (0 obs): Key doesn't match data, or column:value combo absent, or all observations dropped. Trace back to verify key.

### Placeholder Failures
- [DATA] fails: Column doesn't exist (key mismatch) or has empty values. Verify exact header match.
- [NUMBER] fails: Column has non-numeric content ("N/A", "-"). Filter or use different column.
- Failures > 10% of rows: Column reference is fundamentally wrong.

### Place Resolution
- StatVars with place failures: observationAbout values can't resolve. Use FIPS/DCIDs instead of place names.
- StatVars with NO observationAbout: Missing place mapping entirely.
- ALL StatVars fail: Geo column mapping is wrong. Switch to FIPS/DCID columns.

### Top Unmatched Input Values
Highest-signal diagnostic — values that matched nothing in the PVMAP.
Classify by pattern: year-like → add observationDate; state/FIPS codes → add observationAbout; numeric → add value,[NUMBER]; categorical → add COLUMN:VALUE rows.

### Auto-Repair Context
If repair changes are listed above (in "Auto-Repair Changes Applied"), they were applied AFTER LLM generation but BEFORE validation:
- Key case fixes (e.g., "year" -> "Year"): The PVMAP generated the wrong case. Generate the CORRECT case next time.
- Placeholder fixes (e.g., [data] -> [DATA]): The PVMAP used wrong placeholder syntax. Use the correct syntax.
- Fuzzy match fixes (e.g., "State FIPS " -> "State FIPS Code"): The PVMAP key was close but not exact. Use the EXACT column header.
- Hallucination cleanup (e.g., "REF_AREA:Reference area:Reference area" -> "REF_AREA:Reference area"): The LLM hallucinated extra key segments.
Do NOT undo any repairs — they improved the PVMAP. Internalize the corrections and generate correctly next time.

## Schema.org Property Warnings
If the key match report or validation error contains "SCHEMA WARNING" or "SCHEMA NOTE":
- **Unknown properties**: Check for typos. Use the exact Data Commons property name (e.g., "gender" not "Gender", "measuredProperty" not "measured_property").
- **Incompatible properties**: The property may still be a valid DC extension. Only flag if it seems truly wrong for the data type.
- **Missing required properties**: observationAbout, observationDate, and value are always required.
DC-only properties (age, race, naics, statType) are expected to NOT appear in schema.org -- this is normal.
