## PVMAP Syntax Rules

**Key matching:** The first column of each PVMAP row is the key. It matches either a CSV column header or a cell value (for COLUMN:VALUE rows). Matching is case-insensitive with substring fallback, but exact matches are preferred. Copy keys exactly from the plan's column names. If a header contains commas, quote the key: "GDP, current prices".

**Property-value pairs:** After the key, columns alternate: property name, property value, property name, property value, etc.
```
key,property1,value1,property2,value2,...
```

**Placeholders:**
- [DATA] inserts the raw cell string (text, codes, dates)
- [NUMBER] parses the cell as a numeric value (measurements, counts, years)
- Named captures: Year,[NUMBER] stores an intermediate; reference later as [Year]-[Month]

IMPORTANT: Use square brackets [DATA] and [NUMBER], NOT curly braces. The downstream processor normalizes these automatically.

**Carry-forward mechanism:** The processor walks columns left-to-right. Rows WITHOUT `value` accumulate properties as context. When a row HAS `value`, all accumulated properties merge to form one StatVarObservation and emit it.

Trace — input row [USA, 2020, 330000000]:
```
"USA"       -> observationAbout=USA         (no value -> carry forward)
"2020"      -> observationDate=2020         (no value -> carry forward)
"330000000" -> value=330M + carried context -> Emit 1 SVObs
```

**variableMeasured:** Auto-built from populationType + measuredProperty + statType + constraint properties. NEVER set variableMeasured directly. NEVER use variableMeasured,dcid:... shortcuts.

**dcs: prefix rules:**
- USE dcs: for Data Commons types, properties, and enum values: populationType,dcs:Person / gender,dcs:Male / isic,dcs:ISIC/B
- DO NOT prefix placeholders: observationDate,[NUMBER] (not dcs:[NUMBER])
- DO NOT prefix raw data: observationAbout,country/[DATA] (not dcs:country/[DATA])
- DO NOT prefix place DCIDs: observationAbout,geoId/06 (not dcs:geoId/06)

**Column omission:** Columns NOT in the PVMAP are automatically skipped. Do NOT use #ignore.

**Quote keys with commas:** "GDP, current prices",value,[NUMBER],...

## Instructions

Follow these steps exactly:

1. **Start from the PVMAP skeleton.** Copy every row. Do not remove any.

2. **For each active column (role != ignored):** Ensure the skeleton row has the correct property and value expression from the plan. LOCKED rows are already correct. OPEN rows need the DC property name filled in.

3. **For each dimension column:** Add COLUMN:VALUE rows for EVERY value in the value dictionary.
   - MAP values: COLUMN:VALUE,dc_property,dcs:dcid
   - DROP_CONSTRAINT values: COLUMN:VALUE (empty — no property-value pairs, the constraint is omitted)
   - DROP_ROW values: COLUMN:VALUE,#Filter,false

4. **Add static-properties row.** On the value row (the row with value,[NUMBER]), append the StatVar blueprint's base_properties: populationType, measuredProperty, statType, and any unit/scalingFactor/measurementDenominator.

5. **Handle multiple measure columns.** If the transformation strategy has action=melt, create separate PVMAP blocks — one per measure column. Each block gets its own value,[NUMBER] row with the appropriate StatVar properties.

6. **Handle DROP_CONSTRAINT entries.** When a dimension value has action=DROP_CONSTRAINT, the COLUMN:VALUE row must NOT carry the constraint property. This produces a "total" StatVar without that dimension's constraint.

7. **Final check.** Verify:
   - Every active column from the plan has a PVMAP row
   - Every dimension value from the dictionaries has a COLUMN:VALUE row
   - observationAbout, observationDate, and value rows are present
   - All DC types/enums use dcs: prefix
   - No placeholders have dcs: prefix
   - Keys match column headers exactly (copy from the plan)

## PLAN_ERROR Escape Hatch

If the plan is structurally impossible to translate into valid PVMAP syntax (e.g., contradictory role assignments, missing required columns, circular dependencies), output ONLY this JSON and nothing else:

```json
{"status": "PLAN_ERROR", "reason": "Brief explanation of what is structurally impossible"}
```

Do NOT use this for uncertainty or preference — only for genuine structural impossibility.

Return a JSON object with all 4 required fields:

```json

  "format_detected": "raw",
  "pvmap_rows": [
    {"key": "ColumnName", "mappings": [{"property": "propName", "value": "propValue"}, ...]},
    {"key": "COLUMN:VALUE", "mappings": [{"property": "dc_property", "value": "dcs:dcid"}]}
  ],
  "validation_notes": "Brief notes confirming plan was followed faithfully",
  "confidence": "high"
}
```

`format_detected`: one of "raw", "pre-formatted", "passthrough".
`confidence`: one of "high", "medium", "low". Should be "high" if plan was fully translatable.
